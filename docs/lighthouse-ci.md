# Бюджет производительности в CI (этап 6)

Каждый push в `master` прогоняет Lighthouse CI по **всем** собранным
страницам (`dist/**/*.html`: главная, `/faq/`, `/contacts/`, `/privacy/`,
`/terms/`, `404`). Прогон — мобильный, с троттлингом (профиль Lighthouse
по умолчанию), три запуска на страницу, оценивается медиана.

Если хоть один порог не выдержан, job `lighthouse` падает, а job `deploy`
не запускается: на прод уезжает только сборка, уложившаяся в бюджет.

| Метрика                | Порог     | Ключ в `lighthouserc.json`        |
|------------------------|-----------|-----------------------------------|
| LCP                    | < 2,5 с   | `largest-contentful-paint`        |
| CLS                    | < 0,1     | `cumulative-layout-shift`         |
| TBT                    | < 300 мс  | `total-blocking-time`             |
| Performance score      | ≥ 90      | `categories:performance`          |
| SEO score              | = 100     | `categories:seo`                  |
| Accessibility score    | = 100     | `categories:accessibility`        |

Best Practices считается, но порога нет: в него входят ошибки в консоли,
а случайная сетевая ошибка раннера не должна блокировать деплой.

## Почему три аудита отключены

`skipAudits` в конфиге — это не «подгонка под зелёный», а обход трёх
проверок, которые в CI физически не могут пройти и не говорят ничего
о качестве сборки:

- **`canonical`** — Lighthouse проверяет статику на `localhost`, а
  `<link rel="canonical">` указывает на `https://kop-team.ru/`.
  Аудит считает это ошибкой «ведёт на другой домен». Убрать canonical
  нельзя — он нужен в проде; менять его на localhost бессмысленно.
- **`is-crawlable`** — на локальном сервере нет `robots.txt` в том виде,
  в каком его отдаёт GitHub Pages.
- **`uses-http2`** — локальный статический сервер работает по HTTP/1.1,
  GitHub Pages отдаёт HTTP/2.

Все три нужно проверить **на живом сайте** после первого деплоя —
разово, руками, через PageSpeed Insights.

## Замеренная база

Прогон на собранной статике (3 запуска на страницу, медиана,
мобильный профиль с троттлингом):

| страница     | Perf | SEO | A11y | BP  | LCP     | CLS   | TBT  |
|--------------|------|-----|------|-----|---------|-------|------|
| `/`          | 98   | 100 | 100  | 100 | 2061 мс | 0.000 | 0 мс |
| `/faq/`      | 100  | 100 | 100  | 100 | 1512 мс | 0.000 | 0 мс |
| `/contacts/` | 100  | 100 | 100  | 100 | 1514 мс | 0.000 | 0 мс |
| `/privacy/`  | 100  | 100 | 100  | 100 | 1515 мс | 0.000 | 0 мс |
| `/terms/`    | 100  | 100 | 100  | 100 | 1513 мс | 0.000 | 0 мс |
| `404`        | 100  | 100 | 100  | 100 | 1522 мс | 0.000 | 0 мс |

На главной LCP-элемент — портрет тренера. Запас до порога 2,5 с
держится за счёт трёх вещей: responsive `preload` портрета в head
(`src/data/hero.ts`), ширины 680 px ровно под телефон и отдельного
качества AVIF для этой картинки (`quality` в `tools/media.config.mjs`).
Если менять портрет — перепроверить LCP: при 49 КБ вместо 27 КБ он
упирался в 2,49 с.

## Локальный прогон

```
npm run build
npx @lhci/cli autorun
```

Отчёты складываются в `.lighthouseci/report/`.
